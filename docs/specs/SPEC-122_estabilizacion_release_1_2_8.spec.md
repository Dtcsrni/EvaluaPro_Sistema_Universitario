## Contexto

El E2E remoto confirmó que el fixture Burn de igual versión quedó registrado, pero agotó la espera del resultado visible. La fuente de la GUI etiqueta un resultado fallido como `5 Resultado · error`, mientras el runner exigía `activo`; el ajuste local espera el estado de error y una nueva E2E debe confirmar el comportamiento runtime. La matriz funcional extendida también excedió por poco los 60 segundos al esperar que el trabajo OMR alcanzara `completed`. El banco y su revisión conservan 20 reactivos; para esta prueba integral, el examen que se genera y procesa por PDF/OMR se reduce explícitamente a una página y cinco preguntas, manteniendo los mismos pasos del flujo y el timeout vigente. Esta revisión mantiene la cobertura dentro de SPEC-122 y alinea la aserción del E2E con el contrato visual y la carga de la prueba con su propósito.

La promoción estable de 1.2.8 reúne defectos encontrados en CI local/remoto, el Stable Gate y la validación del Installer Hub. Se consolidan aquí las decisiones aprobadas en SPEC-115 a SPEC-121 para que una sola unidad de trabajo describa los gates completos y su relación. Las fichas originales se conservan como detalle del incidente, aprobación y trazabilidad; este documento no reemplaza ni reduce sus criterios. La primera inspección visual del bundle 1.2.8 detectó que la estimación de tiempo de la pantalla de ejecución se recorta en el ancho normal, por lo que se añade un criterio verificable de legibilidad antes de promover el candidato. La falla local del post-install también reveló que el JSON de handoff estaba dentro del directorio de aplicación que MSI puede reemplazar; el error activaba la limpieza de fallo y podía dejar incompleta una instalación previa. La última inspección visual encontró además que el build local reutilizaba un `dist-docente` anterior a los cambios fuente; la prueba contra el servidor de desarrollo pasó, pero el instalador contenía CSS viejo. Esta actualización unifica el requisito de frescura del artefacto y su regresión en esta spec paraguas, sin crear una ficha separada. La validación visual local también mostró que Windows puede mantener el Escritorio delante del Hub recién lanzado; el test debe esperar una ventana visible sin cobertura por un tiempo acotado y dejar que el operador la traiga al frente, sin forzar el foco. La inspección de los artefactos generados detectó que `docs/AUTO_ENV.md` mezcla variables de herramientas legadas con variables del runtime, mientras que las fuentes Mermaid de arquitectura aún representan MongoDB como almacenamiento local y cloud. Esta versión fija SQLite para la fuente docente local y para el read-model del portal, separa las variables de scripts del runtime publicado y exige que los diagramas renderizados estén sincronizados con sus fuentes. El registro de producción del App Host muestra una excepción durante `MainWindow_Closing`: tras esperar el apagado asíncrono, un segundo `Close()` puede ejecutarse mientras WPF ya procesa otro cierre. Esta actualización añade un contrato idempotente de cierre y una regresión para esa carrera, sin crear una spec aislada del incidente. Las pruebas de contrato también conservan expectativas antiguas que contradicen la arquitectura docente vigente: el App Host no reconcilia accesos directos (lo hace el instalador) y el MSI docente incluye contratos JSON, mientras los módulos PowerShell pertenecen al payload Burn para sabores heredados. La primera reparación real de 1.2.8 detectó además una carrera de actualización Burn: el MSI nuevo finalizó correctamente, pero la desinstalación posterior de un bundle relacionado retiró el payload que el helper debía validar. El log precisa que el bundle relacionado tenía la misma versión 1.2.8.0 y que el MSI estaba ausente al iniciar el nuevo bundle. Burn instaló el MSI y después desinstaló el bundle previo; el MSI de ese bundle retiró el producto recién aplicado. La reparación siguiente funcionó cuando ya no quedaba ese bundle relacionado. Se añade una protección fail-closed para el caso de un bundle relacionado de la misma versión: detenerse después de planificar, antes de `Apply`, y conservar la instalación; el usuario deberá relanzar la actualización cuando exista una relación de versiones segura. La reparación de misma versión sin otro bundle relacionado sigue permitida. La corrida remota registró una nueva espera agotada de 90 segundos para el conflicto de versión y subió captura, pero el error del job no incluye la snapshot UIA que leyó el runner ni las líneas diagnósticas del log del Bootstrapper Application. Esta actualización hace que la falla conserve y emita ese contexto acotado en el log CI, para separar un error de detección Burn de un desacuerdo de texto UIA en la siguiente validación. Por último, la inspección de productos MSI mediante `Win32_Product` produjo reconfiguraciones automáticas de Windows Installer; el QA local debe evitar esa clase y usar comprobaciones de solo lectura para no activar autorreparación. El Stable Gate #98 confirmó sus gates del candidato y completó `qa:full`, pero el control final rechazó la promoción porque una prueba de backend escribió `apps/backend/reports/qa/latest/global-grade.json` dentro del árbol de fuentes. La ruta dependía de `process.cwd()`, que cambia entre ejecución desde la raíz y `npm -C apps/backend`; el reporte debe resolverse desde la ubicación estable del test al `reports/qa/latest/global-grade.json` de la raíz del repositorio, y una regresión debe proteger esa invariante.

La E2E del SHA `dbfa3ffe` confirmó que Burn sí detecta el bundle relacionado y detiene antes de `Apply`, conserva la instalación y muestra el mensaje de que no aplicó cambios. El timeout restante se debía a que el panel de error conservaba el título genérico `Resumen de error`, aunque el título de la etapa era específico. Esta revisión asigna el título del conflicto al resumen visible y expone su nombre dinámico a UI Automation, manteniendo la validación del título, explicación y stepper en el E2E.

La E2E visual del SHA `16d700226a5b6befc441913e84c5ad109ab401b5` volvió a confirmar el bloqueo seguro antes de `Apply`, el texto explicativo y `5 Resultado · error`, pero agotó la espera porque el título específico no apareció en la snapshot UI Automation pese a existir un binding XAML a `Text`. El render también asignaba explícitamente `AutomationProperties.SetName`, pero el nuevo run `39364006894` reprodujo la ausencia del título en el árbol UIA. El título se cambia a un control `Label`, cuyo contenido y nombre accesible se asignan juntos durante el render; la E2E debe confirmar el título, la explicación y el stepper en el bundle reconstruido.

El run `39366354878` confirmó que el título seguía ausente tras navegar al paso final: la vista de progreso ocultaba su resumen al mostrar `ResultStepPanel`. La vista final ahora incluye una tarjeta de error con título y explicación vinculados al estado, visible solo cuando existe un fallo; así el usuario y UI Automation reciben el contexto completo en el resultado que realmente se presenta. La regresión verifica que los campos estén en el panel final, se actualicen desde el modelo y la espera E2E confirme el título junto con la explicación y el stepper.

El run de Installer Windows `39368283159` completó correctamente el build y la E2E docente del bundle, pero falló antes de las aserciones visuales del PDF porque el runner Windows no tenía `pdftoppm` disponible (`spawnSync pdftoppm ENOENT`). La previsualización rasterizada forma parte de la E2E real en Edge; por ello el workflow instalará una versión fijada de Poppler desde su distribución oficial, verificará el SHA-256 del archivo, ejecutará `pdftoppm -v` y agregará su directorio a `PATH` antes del paso Playwright. Una prueba de contrato evita que se omita o desordene esta preparación. El fallo previo no aporta evidencia sobre el render visual: la prueba todavía debe pasar en el runtime Windows.

El primer intento de la instalación fijada de Poppler en Windows descargó el archivo correcto, comprobó el SHA-256 y localizó `pdftoppm.exe`; falló porque Windows PowerShell 5 trata el `stderr` que `pdftoppm -v` usa para imprimir su versión como `NativeCommandError`. La comprobación ahora ejecuta el proceso con `Start-Process`, captura `stdout` y `stderr` en archivos separados y valida el código de salida y la versión sin convertir la salida diagnóstica válida en error de PowerShell. La regresión de contrato protege este mecanismo; la siguiente E2E Windows debe confirmar la instalación real y continuar hasta captura y descarga.

El run de Windows `39372851883` pasó build, firma de manifiesto, smoke Burn, Chromium, Edge y la instalación fijada de Poppler; la E2E falló al capturar «2 Preparar · activo» durante reparación, aunque UI Automation ya reportaba ese paso. Los logs sitúan la captura 439 ms después de la captura inicial de la ventana y el análisis registró cero píxeles claros. El runner ahora exige dos observaciones UIA consecutivas del paso y espera 500 ms antes de la única captura visual; mantiene bloqueante la verificación de contenido visible, sin reintentar la operación ni ampliar sus timeouts.

El Stable Gate #99 completó los gates funcionales, pero QA informó un archivo fuente modificado. El log confirma que `test:dataset-prodlike:ci` exportaba directamente a `tests/fixtures/prodlike/prodlike-anon.json.gz`, la salida predeterminada del exportador y un archivo versionado. La causa queda reproducida por el contrato de rutas; el nuevo runner usa `reports/qa/generated/`, y una prueba de integración calcula el SHA-256 del fixture canónico antes y después de exportar, validar e importar para proteger su contenido en Linux y Windows.

El Stable Gate #100 completó la promoción del candidato, pero el job posterior de publicación se detuvo antes de despachar `CI Installer Windows`. El log identifica un borrador `v1.2.8` no recuperable porque el gate exige una tag Git que apunte al candidato. Sin embargo, el workflow de instalación crea el borrador con `target_commitish` igual al SHA validado y GitHub puede no crear la tag hasta publicar. El guard debe verificar el SHA exacto mediante la referencia de tag cuando exista o, únicamente si no existe, mediante `target_commitish` del borrador; cualquier discrepancia, release publicado o borrador con otra tag debe seguir bloqueando la publicación. No se elimina ni se retargetea un borrador discrepante. El Stable Gate #102 confirmó que `GET /commits/v1.2.8` devuelve HTTP 422 cuando el tag aún no existe, antes de poder despachar el instalador. El preflight consulta primero `GET /git/ref/tags/v1.2.8`: solo si devuelve 2xx resuelve el commit con `GET /commits/v1.2.8`; un ref ausente conserva el 404 verificable y cualquier otro error, incluido un fallo al resolver un ref existente, bloquea la publicación.

El último run del borrador falló antes de instalar: el checkout de la tag no contiene artefactos generados y el workflow descargaba solo el EXE y el sidecar, aunque el runner lee `dist/installer/EvaluaPro-release-manifest.json`. Se corrige de forma unificada para los flujos draft y público, descargando el manifiesto oficial, verificando digest/longitud y validando versión, commit y flavor antes de iniciar cualquier instalación. La regresión se limita al contrato de ambos pasos y a la E2E del asset afectada.

## Requisitos Funcionales

- **REQ-028 — E2E del asset usa manifiesto de release verificado:** El flujo draft/público descarga el manifiesto publicado en la ruta que consume el runner, valida digest, versión, commit candidato y flavor `docente-local`; falla antes de instalación cuando falta o no coincide.

- **REQ-001 — Checkout candidato estricto (SPEC-115, SPEC-117):** Mantener bloqueantes los controles de limpieza iniciales, intermedios y finales. Se toleran exclusivamente diferencias CRLF/LF sin cambios semánticos en archivos rastreados y sin preparar; incluye manifests JSON históricos incompatibles con `.gitattributes`. Se rechazan modificaciones preparadas, archivos sin seguimiento, cambios de tipo/modo y cambios de contenido; reportar etapa y rutas.
- **REQ-002 — Aislamiento de E2E y evidencia (SPEC-116):** Ejecutar capturas, scratch y resultados fuera del checkout candidato; preservar evidencia útil como artefactos y señalar la primera etapa que altere fuentes. No restaurar fuentes ni ampliar retries/timeouts.
- **REQ-003 — QA local fail-closed (SPEC-118):** `qa:full` falla si un gate requerido tiene reporte ausente, inválido o `ok: false`; conserva diagnósticos y aplica la misma condición que la promoción estable.
- **REQ-004 — Arranque y render del Installer Hub (SPEC-119):** El E2E identifica la ventana y proceso del bundle probado, separa etapas de arranque/detección/captura, espera hasta 60 segundos a que la ventana quede visible y sin cobertura para permitir activación manual en Windows, no fuerza el foco, exige dos observaciones UIA consecutivas del paso esperado antes de capturar, rechaza capturas blancas o estados UIA incorrectos y cierra únicamente el árbol que inició.
- **REQ-005 — Validación MSI no destructiva local (SPEC-120):** El build local extrae y comprueba el MSI sin registrar o retirar producto en el host. Las transacciones MSI se prueban en runner Windows efímero con limpieza verificada.
- **REQ-006 — Versión visible dinámica (SPEC-121):** El resumen y encabezado del Installer Hub muestran una misma versión proveniente del bundle actual; contratos y E2E detectan versiones literales obsoletas.
- **REQ-007 — Puerta de promoción:** Ejecutar todas las pruebas locales aplicables antes de enviar el SHA a CI/CD; después exigir los gates remotos completos, dos pasadas visuales consecutivas del mismo candidato y evidencia verificable antes de declarar estable o publicar.
- **REQ-008 — Manifiesto QA coherente con EOL y salidas fuera de fuentes:** `workingTreeClean` y `dirtyPathCount` deben usar la misma comparación semántica del guard; solo diferencias EOL unstaged son limpias. Cambios staged, semánticos o sin seguimiento siguen contando como suciedad. Los tests que generan reportes deben resolverlos desde su archivo fuente en la ruta canónica de reportes del repositorio, nunca bajo paquetes de código versionados, independientemente del directorio de ejecución.
- **REQ-009 — Texto de progreso legible:** La estimación de tiempo y su explicación completa deben permanecer visibles y accesibles durante la ejecución en el tamaño normal y el tamaño compacto soportado; el texto debe envolver o acortarse de forma semántica, sin recorte horizontal, superposición ni pérdida del nombre accesible.
- **REQ-010 — Handoff de instalación durable y no destructivo:** Las solicitudes/respuestas privadas entre Burn y su helper deben vivir fuera de todas las carpetas administradas por MSI. Antes de planear cualquier operación se rechazan rutas de instalación que se solapen con el handoff. Ante error antes del post-install, Burn conserva el handoff para diagnóstico y no limpia una instalación que ya existía; el rollback de residuos solo puede operar sobre una instalación nueva/incompleta y nunca sobre `data`.
- **REQ-011 — Evidencia WCAG para colores nuevos:** Cada declaración CSS de color crudo que se agregue a la rama debe tener un comentario `WCAG AA` cercano y su combinación de foreground/background debe figurar en la auditoría automatizada de contraste. El preflight local y CI deben ejecutar el mismo guard sobre el diff candidato.
- **REQ-013 — Diagnóstico útil de drift de API:** Cuando el historial de API pública o de composición difiera de la API extraída, el reporte identifica exports agregados, eliminados o cuya firma cambió; si solo difiere la estructura, informa que debe revisarse el orden o la forma del snapshot. No oculta ni acepta el drift. Las pruebas comprueban estos casos y que el gate siga rechazando el contrato hasta registrar la evolución SemVer correspondiente.
- **REQ-014 — Recorrido visual responsive de docente:** El E2E operativo del docente recorre cada sección principal en escritorio, tablet y móvil; después de navegar verifica ausencia de desbordamiento horizontal y controles inaccesibles/solapados, y conserva capturas de las pantallas. Los títulos y etiquetas de estado visibles no pueden quedar recortados por sus contenedores. Las reglas de superficies reconocen únicamente clases raíz completas y no deben convertir subpartes BEM (`*-panel__*`, `*-card__*`) en tarjetas.
- **REQ-012 — Runtime PDF y diagnóstico de gates visuales:** Todo gate que invoque el preview rasterizado de PDF instala sus renderizadores del sistema antes del E2E; el workflow Windows descarga Poppler desde su distribución oficial con versión y SHA-256 fijados, valida que `pdftoppm` se ejecute y lo agrega a `PATH`. El workflow mantiene un contrato que detecta omisión, hash incorrecto o paso fuera de orden. Si falla arquitectura, el artefacto del job incluye el reporte JSON específico de ese gate. La aserción del E2E de preview conserva el identificador de solicitud de la respuesta para correlacionarlo con los logs sin revelar datos sensibles.
- **REQ-016 — Frescura del payload docente:** Al empaquetar `docente-local`, generar el bundle docente y el backend desde las fuentes del checkout actual antes de copiarlos al staging; la mera presencia de `index.html` o `index.js` no autoriza reutilizar un artefacto previo. La guardia valida los assets copiados y vuelve a validar el bundle dentro del ZIP extraído del MSI, para que una regresión de compilación o empaquetado falle antes de publicar.
- **REQ-017 — Documentación generada y arquitectura vigente:** `docs/AUTO_ENV.md` distingue variables del runtime de variables usadas solo por herramientas/scripts. Los diagramas de arquitectura lógica y despliegue documentan SQLite para la fuente docente local y SQLite para la vista derivada del portal; ninguna fuente ni SVG generado representa MongoDB como componente del producto. Los artefactos generados deben coincidir con sus fuentes.
- **REQ-018 — Cierre asíncrono idempotente del App Host:** Mientras el App Host espera el cierre coordinado de sus servicios, las solicitudes adicionales de cierre deben permanecer canceladas. El cierre definitivo solo puede ejecutarse una vez que la limpieza concluyó y el manejador autorizó explícitamente esa transición; la continuación asíncrona no debe volver a llamar `Close()` si WPF ya cerró la ventana. La regresión debe proteger el orden del estado y comprobar que un segundo intento no cierre la ventana durante la espera.
- **REQ-019 — Contratos alineados con el flavor docente vigente:** Las regresiones deben reflejar la arquitectura `docente-local`: el App Host no ejecuta reconciliación de accesos directos; WiX/MSI administra esos accesos. Los módulos PowerShell de orquestación se empaquetan en el payload Burn para sabores heredados, mientras el MSI docente contiene el ZIP nativo, `package.json` y los contratos JSON requeridos. Las pruebas rechazan regresiones de este aislamiento sin exigir módulos heredados dentro del MSI docente.
- **REQ-020 — QA MSI sin autorreparación:** Los scripts de QA, build y verificación de instalación no deben consultar `Win32_Product`, porque el proveedor MSI puede iniciar reconfiguración/autorreparación de productos instalados. Las comprobaciones de procesos pueden usar `Win32_Process`; las de instalación deben usar consultas de solo lectura a registro, manifiestos y hashes. La regresión falla si se introduce `Win32_Product` en esos flujos.
- **REQ-021 — Orden seguro de actualización Burn y bundle relacionado:** La actualización o reparación debe impedir que la limpieza del bundle anterior retire el MSI o el payload de la instalación que acaba de aplicar la cadena actual. Si se detecta una relación `Upgrade` con un bundle de exactamente la misma versión del candidato, Burn debe detenerse antes de `Apply`, conservar el estado instalado y mostrar una causa accionable; una reparación de la misma versión sin otro bundle relacionado sigue permitida. El fixture de conflicto debe completar la instalación Burn mediante un paquete ejecutable inerte, no permanente (`DetectCondition="0"`, `Permanent="no"`), y la consulta de registro debe normalizar cada elemento `REG_MULTI_SZ` de `BundleUpgradeCode`; el E2E conserva el log Burn de install/uninstall y diagnostica entradas observadas si el fixture no aparece. Burn solo informa éxito cuando el helper valida el archivo nativo, el manifiesto y los archivos críticos; ante fallo de limpieza relacionada, conserva la instalación existente y muestra un resultado verificable. La regresión cubre upgrade desde bundle previo de versión menor, reparación repetida sin bundle relacionado, rechazo antes de `Apply` del bundle `Upgrade` de igual versión y fallo de limpieza relacionada, en un host Windows aislado.
- **REQ-022 — Estado semántico accesible del conflicto en E2E:** Al bloquearse antes de `Apply`, el resumen del Installer Hub muestra `Actualización detenida por conflicto de versión`, su nombre de UI Automation refleja el mismo texto dinámico, la explicación confirma `no se aplicaron cambios` y el stepper muestra `5 Resultado · error`. El runner de Windows espera ese estado terminal y conserva la captura; no debe exigir `activo` para una pantalla que correctamente indica error. Las pruebas de contrato protegen el contenido visual y el nombre accesible.
- **REQ-023 — Carga OMR acotada en el journey integral:** El fixture conserva la creación, confirmación, revisión y publicación de los 20 reactivos del banco. El examen generado para PDF/OMR usa explícitamente una página y cinco preguntas, validando ambos valores en la GUI antes de guardar la plantilla. Se mantienen los pasos del flujo integral y el timeout actual; no se permiten reintentos que oculten lentitud.
- **REQ-024 — Diagnóstico de conflicto Burn en CI:** Si la GUI no llega al estado terminal de conflicto, el runner imprime una snapshot UIA de hasta 2,400 caracteres y copia el log Burn de la operación al artefacto; el log del job filtra líneas por detección de bundles relacionados, planificación, `Apply` y conflicto, sin volcar logs MSI completos.
- **REQ-026 — Fixture prodlike inmutable durante CI:** El paso `test:dataset-prodlike:ci` genera, valida e importa una copia bajo `reports/qa/generated/`, y Git ignora esa ruta; no escribe ni reescribe el fixture versionado `tests/fixtures/prodlike/prodlike-anon.json.gz`. Una prueba calcula el hash del fixture antes y después de las tres etapas y comprueba que se conserve idéntico. El runner propaga cualquier error de proceso o etapa y no continúa con importación parcial.
- **REQ-027 — Recuperación fail-closed del borrador estable:** Antes de despachar publicación, el Stable Gate valida que un release existente sea un borrador con la tag esperada. Si existe una referencia Git para la tag, su commit debe ser exactamente `SOURCE_SHA`; si no existe, `target_commitish` del borrador debe ser exactamente `SOURCE_SHA`. Un release publicado, una tag distinta o un SHA distinto bloquean el flujo. Si no hay release, una tag existente solo se acepta cuando apunta al mismo `SOURCE_SHA`. El gate no elimina, publica ni retargetea borradores; la publicación y las E2E del asset draft y público siguen siendo pasos separados y bloqueantes.

## Criterios de Aceptación

- **CA-028:** La E2E del asset draft y público valida que el workflow descarga `EvaluaPro-release-manifest.json` desde los assets del release, verifica SHA-256 y longitud, lo deja en `dist/installer/` y confirma `version`, `build.version`, `build.commit` y el único flavor `docente-local` antes de ejecutar el runner. El test de contrato falla si se omite la descarga, la verificación o el orden previo a la instalación.

- **CA-001:** El guard compartido admite cualquier normalización EOL que no cambie el contenido de archivos rastreados sin preparar y falla ante todo cambio material, staged, sin seguimiento o de tipo/modo.
- **CA-002:** Todas las salidas E2E del Stable Gate quedan fuera del checkout y siguen adjuntas al run para auditoría.
- **CA-003:** Una salida QA roja, inválida o ausente hace fallar `qa:full` local y la promoción estable.
- **CA-004:** Las pruebas locales del Hub producen capturas válidas y verifican proceso/estado/versión; si Windows deja otra ventana delante, esperan hasta 60 segundos con instrucción visible al operador y fallan de forma explícita sin cambiar el foco; no ejecutan transacciones MSI en el host local.
- **CA-005:** El candidato supera las suites locales relevantes antes de CI, los gates requeridos y dos ejecuciones visuales consecutivas sobre el mismo SHA; ningún `skipped` no planeado, retry oculto o evidencia vieja constituye éxito.
- **CA-006:** La spec pasa la auditoría SDD y sus fichas de origen mantienen trazabilidad a pruebas existentes.
- **CA-007:** Un checkout con únicamente drift CRLF/LF produce manifiesto QA limpio y no contradice el guard; cambios semánticos o staged continúan bloqueando promoción.
- **CA-008:** Las capturas del E2E visual de ejecución en tamaño normal y compacto muestran el texto de progreso completo, sin recorte ni superposición; UI Automation expone el mismo texto legible. La regresión protege la propiedad de wrapping y la segunda validación se ejecuta sobre el bundle reconstruido.
- **CA-009:** Una simulación local elimina el directorio de instalación como lo haría un upgrade fallido y confirma que el request del helper sigue presente fuera de ese directorio; los paths iguales o ancestro/descendiente se bloquean antes de `Plan/Apply`; un fallo con instalación preexistente omite desinstalación/limpieza destructiva; los datos de usuario permanecen fuera de la limpieza. La prueba no accede a la instalación productiva.
- **CA-010:** Los colores de KPI y paneles señalados por el CI tienen comentario `WCAG AA`, sus contrastes se calculan y prueban contra la superficie efectiva más clara, y la regresión falla si se quita el comentario o el par auditado.
- **CA-011:** Seleccionar `ux-visual-check` instala Poppler antes del E2E; la prueba de contrato falla si se retira esa condición. El flujo Windows del Installer Hub descarga Poppler `26.09.0-0`, comprueba el SHA-256 oficial, encuentra un solo `pdftoppm.exe`, ejecuta `-v` con captura segura de stdout/stderr en Windows PowerShell, valida código de salida y versión, y lo coloca en `PATH` antes de la E2E PDF. La prueba de contrato falla ante omisión, drift de versión/hash, comprobación de proceso frágil o cambio de orden. La publicación de `perf-report` incluye `clean-architecture.json`; una respuesta HTTP fallida en el preview deja su status e identificador de solicitud en el reporte de Playwright.

## Enmienda aprobada v1.29.0 — recuperación verificada del borrador estable

### Contexto

Evidencia adicional del run #39530939924: la validación de descarga, manifiesto y sidecar concluyó correctamente; el runner E2E falló después en `installer-hub-e2e-docente.ps1:2359` al acceder a `releaseManifest.version`. El fallo observó `releaseManifest.version` ausente dentro del runner aunque el paso previo terminó las comprobaciones del manifiesto. La corrección pasa la ruta exacta al runner, carga y valida el esquema una sola vez y emite diagnóstico de ruta/esquema ante ausencia o forma inválida; la regresión cubre ese contrato sin silenciar errores.

En CI #770, el bundle candidato `7af46bb4a864e774e2dbfd987c43efe49b4100c4` pasó build, E2E de instalación/repair/upgrade/uninstall y validación visual PDF en Edge. La descarga posterior del mismo EXE desde el borrador `v1.2.8` verificó HTTP, longitud y SHA-256, pero el job se detuvo antes de instalar al comparar el manifiesto candidato con `target_commitish=4ccde020b85906dba340d8473977b0fc027afc92`. No hay tag Git `v1.2.8`; el borrador conserva assets del candidato y apunta a un SHA anterior. El commit `40c6c0b` contiene solo actualizaciones de evidencia documental después del candidato.

La regla vigente de REQ-027 bloquea cualquier borrador cuyo SHA no coincida con el candidato y prohíbe retargetearlo. Esta propuesta agrega una excepción de recuperación estricta para el caso de un borrador aún privado, sin tag Git y con todos los assets demostrablemente vinculados al candidato; no permite recuperar releases publicados, tags existentes ni assets ambiguos.

### Requisitos propuestos

- **REQ-029 — Recuperación verificada de borrador sin tag:** El gate puede actualizar `target_commitish` al `SOURCE_SHA` solo si el release existente tiene exactamente la `RELEASE_TAG` esperada, `draft=true`, `prerelease=false`, `published_at=null`, y la referencia Git de esa tag está ausente por un 404 confirmado. Errores HTTP distintos de ausencia bloquean.
- Antes de cambiar metadata, el gate valida que `SOURCE_SHA` sea ancestro de `main` y que versión/tag coincidan. El job de publicación reemplaza los assets solo con el bundle del SHA candidato ya probado; antes de ajustar el target verifica versión, commit, flavor `docente-local`, longitudes y SHA-256 tanto local como en los assets remotos. La recuperación falla cerrada si falta un asset, hay duplicados, los hashes no coinciden o el manifiesto refiere otro SHA.
- La acción no crea una segunda release ni elimina ni publica el borrador. El pipeline puede reemplazar únicamente los assets esperados mediante el flujo normal de publicación, después de que el bundle candidato haya pasado su E2E; valida que el manifiesto, sidecar, digest y tamaño remoto coincidan antes de modificar `target_commitish`. Ante cualquier discrepancia, conserva la metadata del borrador y falla cerrado.
- Tras actualizar el target, el gate vuelve a consultar y comprobar la metadata. La validación del asset descargado debe pasar antes de permitir publicación.
- **REQ-030 — Reutilización trazable de E2E del mismo binario:** No se repite el E2E visual/runtime del instalador si el EXE descargado tiene el mismo SHA-256, versión, commit y flavor que un bundle del mismo `SOURCE_SHA` cuyo E2E visual/runtime completo ya pasó. En ese caso se exige descargar de nuevo el asset, verificar sidecar/manifiesto/hash y asociar explícitamente la evidencia E2E existente con el mismo digest. Si cambia cualquier dato de identidad o no existe evidencia visual/runtime para ese digest, se ejecuta el E2E del asset descargado y se inspecciona visualmente su evidencia antes de publicar.

### Criterios de aceptación

- **CA-029:** Pruebas de contrato cubren la única recuperación permitida (borrador exacto, sin tag, assets/manifiesto candidatos válidos) y rechazan release publicado, prerelease, tag distinta, tag existente, error de API, SHA ajeno o inconsistente, versión/flavor incorrectos, digest/longitud incorrectos, assets ausentes/duplicados y manifiesto ausente.
- **CA-030:** Una regresión verifica que la revalidación posterior confirma `target_commitish=SOURCE_SHA` y que no hay llamadas de eliminación, reemplazo ni publicación en la ruta de recuperación.
- **CA-031:** La rama de recuperación ejecuta solo los contratos del gate/manifest y la E2E del asset fallida. El E2E visual/runtime se reutiliza únicamente con igualdad byte-a-byte (SHA-256) y coincidencia de SHA candidato; el reporte muestra la referencia exacta de la corrida y la inspección de sus capturas.

La enmienda fue aprobada por el usuario el 2026-10-21. Se autoriza cambiar workflows, código y pruebas dentro del alcance, y modificar metadata del borrador únicamente tras verificar las precondiciones de REQ-029. No se autoriza borrar ni publicar antes de que todos los gates pasen.

## Reutilización de evidencia del instalador candidato

El despacho manual de publicación puede recibir `candidate_run_id` para reutilizar el artefacto inmutable del run del instalador. Antes de aceptarlo, el flujo verifica que el run pertenece a `CI Installer Windows` en `main`, corresponde al SHA completo candidato y contiene un único job exitoso con los pasos de E2E completa del bundle, E2E visual de PDF y publicación de evidencia aprobados. La validación comprueba que el SHA candidato siga siendo ancestro de `main`, la versión y flavor docente-local, el manifiesto, el sidecar y el SHA-256 del artefacto descargado. Si falta una condición, falla cerrado.

El build de Windows se omite solo cuando se solicita explícitamente esa reutilización. Al descargar el asset del borrador se repiten la comprobación de manifiesto, sidecar y digest. La E2E de instalación del borrador se omite solo si el digest del EXE coincide exactamente con el artefacto candidato cuya E2E pasó; la descarga pública se verifica de nuevo y su E2E solo se omite si su digest coincide con el digest ya verificado en el borrador. Cualquier diferencia de digest conserva la ruta completa de E2E de esa etapa. De esta forma se evita volver a instalar y probar bytes idénticos, a la vez que se prueban los límites de distribución y la identidad del asset.

Las pruebas de contrato comprueban la selección del run, la evidencia de pasos requerida, la procedencia del artefacto y el comportamiento de comparación/fallback por digest. No reemplazan las E2E del producto ante cambios de payload.


## Pushes de control a main sin E2E redundantes

La resolución de cambios en `push` a `main` aplica la misma allowlist estricta de controles de release, más la carpeta de evidencia de la versión activa. Solo si el diff está disponible, no vacío y todos sus paths pertenecen a ese alcance, el resolver omite el build y las E2E del instalador. Ante SHA base inválido, diff vacío/no clasificable o cualquier path fuera del alcance, conserva la ejecución completa. Los push de tags y los cambios de payload siguen el flujo normal. Se añaden aserciones de contrato para la clasificación del push y el fallback fail-closed.

## Enmienda aprobada v1.34.0 — ejecutar la verificación del draft al reutilizar el candidato

### Hallazgo y causa

El run 39609025958 reutilizó correctamente el bundle del run 39569392976: SHA fuente, manifiesto, assets y digest coincidieron.
