# Inventario de ciclo de vida de recursos API

Revisión inicial del router backend y `apps/backend/prisma/schema.prisma` para SPEC-070. El inventario de rutas completo está en [`CRUD_CATALOG.md`](./CRUD_CATALOG.md); contratos y schemas están en [`openapi.json`](./openapi.json) y en los validadores Zod fuente.

La matriz enumera individualmente cada modelo Prisma. `npm run api:contract:check` compara ambos inventarios y falla ante modelos omitidos o referencias obsoletas. La clasificación explícita de seguridad/append-only/externo limita el CRUD genérico, pero no saca el modelo del inventario.

`Acción especializada` significa que el dominio versiona, archiva, confirma, resuelve o finaliza en lugar de editar/borrar filas directamente. `Gap` significa que aún falta comprobar o cerrar la operación por API y correspondencia con la GUI; no implica que se deba exponer una mutación genérica.

## Ejecución por fases

La cobertura de todos los modelos está inventariada, pero no significa que cada operación ya esté implementada o validada. Cerrar cada fase requiere ruta/SDK cuando corresponda, permiso y validador explícitos, persistencia por servicio de dominio, auditoría e idempotencia para escrituras repetibles, prueba de contrato/integración y lectura del mismo estado en GUI.

| Fase | Recursos | Estado | Criterio de cierre |
| --- | --- | --- | --- |
| 1. Contrato y autenticación | OpenAPI, preflight, sesión, permisos, lease y SDK base | Implementada en foco; la auditoría de brechas sigue abierta | Catálogo generado, contrato coherente y cliente sin navegador |
| 2. Autoría y bancos | Temas, reactivos/versiones/assets/importaciones, plantillas/preview | Parcial; gaps individuales siguen en la matriz | Alta/lectura/cambio de versión/estado/baja especializada y correspondencia GUI comprobadas |
| 3. Generación y artefactos | Exámenes, progreso, PDFs individuales/consolidados, archivo/restauración | Archivo/restauración de lote implementado en backend/SDK; GUI requiere validación focal | Idempotencia, integridad, paginación y recuperación verificadas para lotes activos/archivados |
| 4. Entregas y OMR | Entregas, códigos, ingestas, jobs, páginas, excepciones y artefactos | Parcial; seguir gaps indicados por recurso | Acciones de dominio auditables, resoluciones recuperables y trazabilidad hasta examen sin escribir notas implícitas |
| 5. Evaluación y publicación | Políticas/versiones, evidencias, calificaciones/revisiones, listas y Classroom | Parcial; cambios de notas/publicación conservan autorización específica | Versionado/concurrencia, cálculo reproducible, privacidad, reconciliación GUI/API y publicación externa verificadas |
| 6. Recursos restantes | Alumnos, periodos, asistencia, temarios, administración, recuperación, sincronización y comercial | Parcial y sujeto a RBAC/entorno | Cada recurso editable tiene su ciclo; seguridad, eventos e integraciones quedan explícitamente especializados/no editables |

## Siguiente trabajo de auditoría

1. Confirmar cada fila contra servicios de dominio y operaciones exactas de GUI, no solo contra rutas registradas.
2. Completar gaps seguros por recurso y añadir pruebas de integración API + prueba de componente para paridad GUI.
3. Auditar los recursos restantes por operación de dominio, incluidas relaciones CRUD de reactivos, bancos, plantillas, entregas, calificaciones y OMR.
4. Añadir filtros, paginación e idempotencia donde el inventario de cargas/reintentos lo requiera.
5. Probar recuperación tras respuesta perdida para generación de examen/lote, importación, calificación y otras escrituras permitidas.
6. Marcar cada fila `validada`, `limitada` o `pendiente` con referencias a suites y decisiones de integridad.

No se considera cerrado el ciclo CRUD global mientras queden filas pendientes. La matriz distingue baja lógica, purga, acciones especializadas e historial inmutable; nunca prescribe mutaciones directas sobre Prisma.
