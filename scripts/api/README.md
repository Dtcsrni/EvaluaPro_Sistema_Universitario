# Cliente API de EvaluaPro

El backend publica `/api`; este cliente usa `fetch` nativo de Node y no inicia navegador ni automatiza la GUI.

```js
import { EvaluaproClient } from './scripts/api/evaluapro-client.mjs';

const api = new EvaluaproClient({
  baseUrl: process.env.EVALUAPRO_URL,
  equipoId: process.env.EVALUAPRO_EQUIPO_ID
});
const docente = await api.login(process.env.EVALUAPRO_CORREO, process.env.EVALUAPRO_PASSWORD);
const estado = await api.preflight({ comprobarClassroom: true });
// Usa IDs devueltos por API, nunca nombres/posición como clave.
```

Cuando la cuenta usa Google, el cliente también ofrece `loginGoogle(credential)`.
`credential` debe provenir del paso interactivo de Google Identity Services de la
aplicación; el SDK lo intercambia en `/autenticacion/google` por la sesión API.
La credencial y el token son secretos efímeros: no los registres ni los persistas.

## Reglas de operación

- El SDK trae helpers para los flujos automatizados más usados; `request()` también permite consumir otras operaciones del catálogo sin navegador. Antes de usar una ruta sin helper, consulta `CRUD_CATALOG.md`, OpenAPI y el validador Zod/servicio real. `request()` genérico no impone las confirmaciones locales de cada helper: el agente debe conservar confirmación/autorización, concurrencia, idempotencia y reglas de dominio de esa operación.
- `preflight()` consulta salud, versión, perfil/permisos y lease cuando el rol lo permite; Classroom es opcional y exige permiso.
- Classroom: `cursosClassroom()`, `actividadesClassroom(courseId, periodoId)`, `alumnosCursoClassroom(courseId, periodoId)` e `historialImportacionesClassroom(periodoId)` leen la misma integración que la GUI. `actualizarMapeoAlumnosClassroom(courseId, payload, { confirmarEscritura: true })` guarda vínculos explícitos de cuentas Classroom con alumnos locales; no crea alumnos. Si se pierde la respuesta del `PUT`, vuelve a consultar `alumnosCursoClassroom()` antes de decidir si reintentas. `previsualizarImportacionClassroom(payload)` no escribe evidencias y `ejecutarImportacionClassroom(payload, { confirmarEscritura: true })` sincroniza las calificaciones seleccionadas a EvaluaPro; no modifica ni publica notas en Classroom. La conexión OAuth y la autorización Google permanecen interactivas.
- Periodos y roster: `listarPeriodos()`, `listarAlumnos()` y `obtenerAlumno()` consultan; `crearPeriodo()`, `actualizarPeriodo()`, `crearAlumno()` y `actualizarAlumno()` requieren `{ confirmarEscritura: true }`; `archivarPeriodo()`, `eliminarPeriodoDev()` y `eliminarAlumnoDev()` requieren `{ confirmarEliminacion: true }` además de los permisos RBAC del backend. Las operaciones de desarrollo continúan restringidas al permiso `*_dev`.
- Temarios: `crearTemarioManual()` y `crearTemarioDesdePdf()` requieren `{ confirmarEscritura: true }`; crear en un periodo que ya tiene temario responde conflicto. `actualizarTemario()` requiere `expectedUpdatedAt`, `motivoCambio` y confirmación, conserva el estado de nodos coincidentes y rechaza eliminar nodos con historial. Cambiar el estado de un nodo también requiere confirmación. `listarTemarios()`, `obtenerTemario()` y `obtenerNodosTemario()` exponen lectura; `listarAuditoriaTemario()` pagina cambios y `listarTodaAuditoriaTemario()` recorre todas las páginas. `eliminarTemario()` requiere `{ confirmarEliminacion: true, expectedUpdatedAt, motivoCambio }`; el backend solo elimina un temario sin avance y conserva el evento de baja en la auditoría aunque el recurso deje de existir. La GUI envía el PDF al endpoint multipart `/temarios/desde-pdf`.
- Temas del banco: `listarTemasBanco()` y `obtenerTemaBanco()` leen por periodo/ID. Crear, actualizar y archivar requieren un `clientRequestId` UUID estable y confirmación (`{ confirmarEscritura: true }`, o `{ confirmarEliminacion: true }` al archivar). Persiste la clave antes del envío y reutilízala solo para la misma operación/payload; si la respuesta es incierta, consulta el tema y `listarAuditoriaTemaBanco()`/`listarTodaAuditoriaTemaBanco()`. Un cambio de payload con la misma clave responde conflicto. La mutación de tema y sus referencias a preguntas/plantillas se audita en una transacción. API y GUI comparten rutas/servicios.
- Papelera de recuperación: `listarPapelera({ limite })` y `restaurarPapelera(itemId, { confirmarEscritura: true })` exponen la vista y restauración manual disponibles en GUI. El backend las restringe a desarrollo y al permiso `docentes:administrar`; no uses la papelera como CRUD general ni para purgar evidencia histórica.
- `listarSesionesAsistencia()`, `crearSesionAsistencia()`, `obtenerRegistrosAsistencia()`, `guardarRegistrosAsistencia()`, reglas, excepciones y resúmenes cubren las rutas de asistencia montadas. Crear sesión, guardar registros/reglas y crear excepciones requiere `{ confirmarEscritura: true }`; las bajas de sesiones/reglas/excepciones requieren `{ confirmarEliminacion: true }` además de RBAC.
- No registres `token`, credencial Google, contraseña, payloads con datos personales ni encabezados de autorización. No pases contraseñas como argumentos de proceso.
- El cliente **no reintenta mutaciones**. `EvaluaproNetworkError.mutationOutcomeUnknown` indica que el servidor pudo haber aplicado el cambio antes de perderse la respuesta; lee el recurso por su ID o consulta su historial antes de decidir qué hacer.
- `crearReactivo()` y `versionarReactivo()` son atajos unitarios al flujo canónico de `importarReactivos()`: conservan el preview/`planHash`, exigen revisar el plan antes de `confirmar()` y la nueva versión requiere `itemId` más `expectedVersion` para detectar concurrencia. No se modifica una versión inmutable en sitio.
- Plantillas: `crearPlantilla()` y `actualizarPlantilla()` requieren `{ confirmarEscritura: true }`; `archivarPlantilla()` y `eliminarPlantilla()` requieren `{ confirmarEliminacion: true }`. Archivar conserva el recurso y referencias históricas; eliminar guarda una copia de recuperación y borra en cascada exámenes, entregas, calificaciones y banderas asociados, por lo que requiere autorización específica y no debe usarse como edición. `obtenerPlantilla()`, `previsualizarPlantilla()`, `previsualizarPlantillaPdf()` y `previsualizarPlantillaPdfVisual()` consumen las mismas rutas/servicios de la GUI. El PDF binario se devuelve como `Buffer`.
- Evidencias de evaluación: `listarEvidenciasEvaluacion()` obtiene una página filtrada por periodo/alumno y `listarTodasEvidenciasEvaluacion()` recorre el historial con `nextCursor`; `obtenerEvidenciaEvaluacion(id)` lee el detalle. `actualizarEvidenciaEvaluacion()` requiere `expectedUpdatedAt`, `motivoCambio` y confirmación para control de concurrencia/auditoría; `archivarEvidenciaEvaluacion()` y `restaurarEvidenciaEvaluacion()` son bajas/altas lógicas con motivo. Solo se modifican evidencias manuales; los registros Classroom conservan su flujo y procedencia original.
- Calificaciones manuales de lista: `listaAcademica(periodoId)` requiere un periodo y lee las filas que presenta la GUI; `guardarCalificacionLista(payload, { confirmarEscritura: true })` guarda por el mismo endpoint y valida las etiquetas y escalas admitidas antes de enviar. El payload requiere un `clientRequestId` UUID persistido por el llamador y la `version` leída. Repetir la clave y el payload devuelve el resultado actual sin duplicar la edición; reutilizar la clave con otros datos responde conflicto. `previsualizarBonoExtracurricular(payload)` exige periodo, alumno y bono entre 0 y 1. `descargarCalificacionesCsv(periodoId)` y `descargarCalificacionesXlsx(periodoId)` exportan las mismas listas por las rutas autenticadas de la GUI y devuelven sus bytes como `Buffer`; requieren un periodo explícito. La GUI vuelve a consultar y reconcilia el valor cuando se pierde la respuesta.
- Políticas de evaluación: `listarPoliticasCalificacion()`/`obtenerPoliticaCalificacion()` consultan políticas del sistema y del docente; `listarAuditoriaPoliticaCalificacion()` pagina eventos y `listarTodaAuditoriaPoliticaCalificacion()` recorre el historial. `crearPoliticaCalificacion()` crea y `versionarPoliticaCalificacion()` publica versiones inmutables; ambos exigen confirmación e `clientRequestId` UUID. `archivarPoliticaCalificacion()` requiere motivo, UUID estable y confirmación de baja; archiva mediante una versión inactiva. La migración añade auditoría append-only con valores antes/después, hash de solicitud y motivo en la misma transacción que la mutación. Solo `lisc_encuadre` y `sv_excel_contract` son familias admitidas; los pesos validados se aplican al cálculo. `configurarPoliticaEvaluacion()` requiere confirmación explícita porque cambia cálculos futuros. El resumen de evaluación conserva ID/código/versión/parámetros usados.
- Alta idempotente de evidencia: `crearEvidenciaEvaluacion(payload, { confirmarEscritura: true })` exige `clientRequestId` UUID y valida que periodo y alumno pertenezcan al docente; `obtenerEvidenciaEvaluacion(id)` recupera el registro por ID. No reusar la clave con payload distinto.
- Códigos de acceso: `generarCodigoAcceso(periodoId, { clientRequestId, confirmarEscritura: true })` usa un UUID estable para recuperar el mismo ID y secreto tras reintentos; valida que el periodo pertenezca al docente y no envía el código a una dirección fija. La clave es opcional en el endpoint HTTP para conservar compatibilidad GUI. `listarCodigosAcceso()` y `obtenerCodigoAcceso()` exponen metadatos, nunca el código. `expirarCodigoAcceso(id, { confirmarEscritura: true })` invalida el código localmente; hay que publicar resultados por separado para transmitir el cambio y la revocación remota no se confirma desde esta operación.
- Entregas: `listarEntregas()` admite filtros y cursor estable; `obtenerEntrega()` conserva aislamiento por docente y omite el correo del alumno. `vincularEntrega()`, `vincularEntregaPorFolio()` y `deshacerEntregaPorFolio()` requieren `confirmarEscritura: true`; el historial se conserva según el flujo del dominio.
- Exámenes: `generarExamenIndividual()` y `generarLoteExamenes()` requieren `{ confirmarEscritura: true }`. El examen individual exige un `clientRequestId` UUID estable guardado por el llamador; el mismo ID y plantilla recuperan el examen después de una respuesta perdida, mientras otra plantilla/docente produce conflicto. Para lotes, `generarLoteExamenes()` exige un `loteId` estable creado y guardado por el llamador antes del primer envío. Si se pierde la respuesta, repetir el mismo payload/ID permite al servicio recuperar o reanudar el lote sujeto a las comprobaciones de plantilla, alumnos, versiones y manifiestos; un lote incompatible devuelve conflicto. Modificar la plantilla, versiones o cohorte significa crear otro lote con un `loteId` nuevo: los PDFs/exámenes generados son artefactos inmutables y el sistema no ofrece edición en sitio. `archivarExamenGenerado()` requiere `{ confirmarEliminacion: true }`; `regenerarPdfExamenGenerado()` requiere `{ confirmarEscritura: true }` y `forzar: true` solo cuando el servidor indique que el examen ya fue descargado. `obtenerExamenPorFolio()`, `descargarPdfExamenGenerado()` y `descargarPdfLoteExamenes()` permiten recuperar datos/PDF por API; las descargas devuelven `Buffer`. `listarLotesExamenes()` y `listarTodosLotesExamenes()` consultan paquetes que ya tienen un PDF consolidado; para un lote parcial cuyo ID conserva el cliente, `progresoLoteExamenes()` informa el estado. El artefacto PDF consolidado aún no tiene archivo/restauración independiente por API; no simules su baja archivando exámenes relacionados. `listarPaginaExamenesGenerados()` expone resúmenes y `nextCursor`; `listarTodosExamenesGenerados()` recorre páginas para procesos que requieran el conjunto filtrado completo. La API limita cada página de exámenes a 200 (100 por defecto) y cada página de lotes a 100 (25 por defecto); claves de respuesta y artefactos se consultan en `obtenerExamenGenerado(id)` o por las rutas específicas de descarga. `listarExamenesGenerados()` mantiene compatibilidad y devuelve la primera página. No reutilices las claves para otro intento lógico.
- `listarReactivos()` filtra por periodo, tema y estado; conserva `nextCursor` sin modificar para solicitar la página siguiente. `obtenerReactivo()` devuelve la versión canónica vigente; `listarVersionesReactivo()`, `listarImportacionesReactivos()` y `obtenerImportacionReactivos()` permiten recuperar estado e historial. La lista de importaciones pagina resúmenes agregados; consulta el detalle por `importId` para descargar sus filas. `listarTodasImportacionesReactivos()` acumula las páginas y detecta cursores repetidos. `revisarReactivo()`, `publicarReactivo()` y `retirarReactivo()` requieren `{ confirmarEscritura: true }` y aplican el RBAC del dominio.
- Un lease configurado se envía como `X-EvaluaPro-Equipo`; este identificador no adquiere el lease. Adquiérelo explícitamente con los endpoints de sincronización.
- `prevalidarCapturasOmr()` no persiste y no requiere confirmación. `crearJobOmr()`, `ingresarPdfsOmr()`, `resolverExcepcionJobOmr()`, `resolverPaginaIngestaOmr()` y `finalizarJobOmr()` modifican el estado OMR y requieren `{ confirmarEscritura: true }`; los dos endpoints de creación además exigen `clientRequestId` UUID. Genéralo y persístelo antes de enviar; ante timeout repite el mismo cuerpo y la misma clave. El servidor devuelve el mismo job; usar la clave con contenido distinto da 409. `listarJobsOmr()` filtra por examen/estado con cursor; `obtenerJobOmr(jobId)`, `obtenerIngestaPdfOmr(jobId)` y `recuperarIngestaPdfOmr(clientRequestId)` permiten recuperar el estado tras perder una respuesta, consultar originales/manifiestos/paquetes/candidatos del lote y continuar en API o GUI. `resolverPaginaIngestaOmr()` vincula una página ambigua con el examen/página generados; requiere motivo y conserva la página en `needs_review`/`autoGradable=false`. Resolver una excepción del job estándar puede dejar una hoja en `accepted`/`autoGradable=true`; esto la prepara para el flujo docente posterior, pero nunca escribe calificaciones. La respuesta OMR se procesa con la orientación original de la página; una rotación probada para leer QR no se reutiliza para leer burbujas.
- Los bytes PDF se devuelven como `Buffer` con `responseType: 'binary'`. El límite de capturas es 200 por solicitud; cada imagen usa el límite configurado por el backend.
- La GUI y la API leen/escriben los mismos servicios y persistencia. La API no omite permisos, revisión, aprobación ni confirmaciones docentes.
- `calificarExamen()` exige `confirmarEscritura: true` y un `clientRequestId` UUID persistido por el llamador; el mismo cuerpo/clave devuelve la nota persistida y usar la clave con otro cuerpo da 409. Úsalo solo con autorización docente explícita. Esta confirmación no publica la nota en Classroom. Si se usa `request('/calificaciones/calificar', ...)` directamente, el llamador conserva la misma semántica y envía el UUID.
- `obtenerCalificacionesExamen()` y `listarSolicitudesRevisionCalificacion()` permiten consultar notas y revisiones; resolver o sincronizar una revisión requiere `confirmarEscritura: true` porque puede cambiar la calificación. Las consultas API reflejan el mismo estado que consume la GUI.

Consulta [`openapi.json`](./openapi.json) para rutas, seguridad, contratos, límites y códigos HTTP; [`CRUD_CATALOG.md`](./CRUD_CATALOG.md) inventaría las operaciones de los routers y [`RESOURCE_LIFECYCLE.md`](./RESOURCE_LIFECYCLE.md) resume las operaciones CRUD/especializadas, límites y brechas por recurso. La auditoría global recurso por recurso sigue abierta; las rutas de escritura heredadas bloqueadas y los recursos sin endpoint no se presentan como CRUD disponible.

El cliente ofrece métodos de ayuda para consulta, importación versionada, revisión,
publicación y retiro de reactivos; generación/reanudación de lotes, Classroom,
lease y calificación. Para cualquier
otra operación catalogada usa `api.request('/ruta', { method, body })`; muchas
actualizaciones del backend usan `POST /:id/actualizar` por compatibilidad. El
contrato lista el validador Zod exacto que debe cumplir el cuerpo.

El catálogo se sincroniza y verifica contra el código fuente. `api:contract:check`
también verifica que todo modelo Prisma tenga un ciclo de vida declarado en
`RESOURCE_LIFECYCLE.md`, incluidos los modelos que no deben exponerse como CRUD genérico:

```powershell
npm run api:openapi:write
npm run api:contract:check
```
